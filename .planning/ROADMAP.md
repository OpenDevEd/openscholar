## Phase Details

### Phase 98: Pre-flight & Hard-Limit Foundation
**Goal**: Ship the per-tier-ready paper-limit constants and prove that a 1000-paper extraction job's reactive query stays under Convex's 8 MB result-size cap before the bump lands in production.
**Depends on**: Nothing (first v7.0 phase; builds on v6.0 `extractionJobs` + `extractionResults` schema)
**Requirements**: LIM-01, LIM-02, LIM-03, GAP-04
**Success Criteria** (what must be TRUE):
  1. `convex/lib/queryBounds.ts` exports `MAX_EXTRACTION_PAPERS_PER_JOB = 1000` (separate from `MAX_EXTRACTION_RESULTS_QUERY`) with every call-site cascade repaired — LIM-01
  2. `EXTRACTION_LIMITS_BY_TIER: Record<SubscriptionPlan, number>` exists with `free/go/pro/enterprise` all resolving to 1000, so v7.1 per-tier tuning requires editing one file only — LIM-02
  3. `getExtractionLimitForUser(ctx)` helper and `getExtractionLimit` reactive query return the caller's per-job limit by routing through `resolveEffectivePlan` — LIM-03
  4. A recorded benchmark run (1000 papers x 7 questions) confirms the `getExtractionResults` payload is <= 5 MB, or the query is migrated to paginated mode before any other v7.0 phase ships — GAP-04
**Plans**: 2 plans
  - 98-01-PLAN.md — Constants + helper + reactive query (Wave 1)
  - 98-02-PLAN.md — Call-site rewiring + payload benchmark (Wave 2)

**Research flag**: MEDIUM — benchmark outcome determines whether Phase 100 must also include pagination migration of `getExtractionResults`.
**Pitfalls mitigated**: PITFALL 1 (200→1000 cascade at 15 call sites with `MAX * 10` multipliers), PITFALL 6 (env-var drift — verify via `npx convex env list`).

### Phase 99: Selection Basket Core
**Goal**: A tab-scoped, dedupe-safe paper basket that survives in-app navigation and can be peeked from anywhere via a drawer — with zero backend dependency so it can ship in parallel with phases 100 and 101.
**Depends on**: Phase 98
**Requirements**: SEL-07, SEL-08, SEL-09, SEL-10
**Success Criteria** (what must be TRUE):
  1. User adds papers in one tab of the app, navigates to a different page, and the basket count is still correct when they return (sessionStorage-backed Zustand store, cleared only on successful job creation) — SEL-07
  2. User adds the same paper via `W123`, `https://openalex.org/W123`, and `openalex:W123` from three different sources and the basket shows exactly one entry — SEL-08 (via `normalizeOpenAlexId` utility)
  3. User clicks the Extraction basket icon from any page and a shadcn `Sheet` drawer opens showing the global count, per-source breakdown, and a "Review & start extraction" CTA — SEL-09
  4. User removes an individual paper from the basket drawer, and while browsing any source list in the app sees a visible "already in basket" indicator next to papers already staged — SEL-10
**Plans**: 2 plans
Plans:
  - 99-01-PLAN.md — Normalize utility + basket store + useAddToBasket hook (Wave 1)
  - 99-02-PLAN.md — Drawer UI components + i18n keys (Wave 2)

**Research flag**: LOW.
**Pitfalls mitigated**: PITFALL 3 (dedupe race on mixed-format OpenAlex IDs), PITFALL 5 (navigation loss on in-memory Zustand), PITFALL 7 (silent cap overflow — single source of truth is the basket store).
**UI hint**: yes

### Phase 100: Backend Wiring + TierSelector Fix
**Goal**: Ship all the Convex actions and server-side hard rejects that Phases 102, 103, and 104 will consume — including the 5-edit fix that finally threads `TierSelector` through `createExtractionJob` → workpool → `createCascadeTiers(tier)`.
**Depends on**: Phase 98
**Requirements**: SEL-05, LIM-07, TIER-01, TIER-02, TIER-03, ZOT-03
**Success Criteria** (what must be TRUE):
  1. User pastes a list of OpenAlex IDs at the Manual tab and sees them resolved and added to the basket via `convex/openalex/actions.ts:resolveManualIds` — SEL-05
  2. When a user attempts to submit an over-limit job (bypassing client-side UI), the `createExtractionJob` mutation hard-rejects with a typed `EXTRACTION_LIMIT_EXCEEDED` error routed to a localized toast via `lib/toast/error-resolver.ts` — LIM-07
  3. User selects the "accurate" tier in the UI, creates an extraction job, and the job row persists `tier: "accurate"` — TIER-01
  4. The workpool action reads `tier` from the job row and calls `createCascadeTiers(tier)` so `auto` runs all 3 tiers, `accurate` runs top tier only, and `cheap` runs bottom tier only — TIER-02
  5. A unit test inspects the constructed OpenRouter request payload and asserts tier selection filters the 3-tier cascade as expected — TIER-03
  6. When a user checks a Zotero item with a DOI, `convex/openalex/actions.ts:resolveByDoi` returns within 10 seconds and the resolved OpenAlex ID is attached to the basket entry — ZOT-03 (wired by Phase 104 UI)
**Plans**: 3 plans

**Research flag**: LOW — smallest feature in the milestone per research, ~5 edits, no migration. `tier` field is optional on `extractionJobs` (new rows only; legacy rows null-coalesce to `auto`).
**Closes v6.0 gap**: EXTR-01 (orphan TierSelector value).
**Anti-feature to NOT ship**: migration of existing v6.0 extraction jobs to the new `tier` field — new rows only.

  2. When the basket reaches the 1000 cap, user sees all remaining "add" checkboxes in every source tab disabled with a tooltip "Basket full — remove N papers to continue" — LIM-05
  3. User bulk-pastes more OpenAlex IDs than the remaining basket capacity allows, and the excess is silently dropped with a toast stating exactly how many papers were dropped (e.g., "Added 400 papers; 200 dropped — basket capacity reached") — LIM-06
  4. User clicks an `<AddToExtractionButton>` mounted in the library, search results, and bookmarks command centers and the selected paper(s) are added to the basket without the page navigating — SEL-11
  5. The sidebar nav "Extraction" item displays a badge with the live basket count (driven reactively by the Zustand store) — SEL-12

  - [x] 102-01-PLAN.md — i18n keys + cap-aware hook + ExtractionCounter component (LIM-04, LIM-06)

### Phase 103: Workbench Views + Selector Page

**Success Criteria** (what must be TRUE):

  3. User clicks "Extract entire collection" on a collection row and all of that collection's items (reading v2.1 `collections` + `libraryItemCollections`) are staged into the basket in one click — SEL-03
  4. User bulk-selects papers from the Search Results tab (reading from `app/results/[searchId]`) and adds them to the basket — SEL-04
  5. User runs a full-text search over paper titles/authors/answers in a loaded job and sees the result subset update live, debounced via React 19 `useDeferredValue` so 1k-row filter storms do not freeze the UI — WB-04

  8. User clicks any citation in any view and a highlighted evidence drawer opens rendering the verbatim `source.text.slice(evidence_start_char, evidence_end_char)` with a parsing-source badge — never the LLM's `evidence_quote` field — WB-07
  9. User exports the currently-filtered result subset as CSV, JSON, or XLSX and the export payload matches the filter state (reusing existing v6.0 export helpers) — WB-08
  10. User paginates the table, card, and split views with "X-Y of Z papers" counts that reset correctly when filters change — WB-09
  11. Every paper row/card in every view renders a `parsingSource` badge (`pmc` / `arxiv` / `unpdf` / `gemini` / `abstract_only`), including inside the evidence drawer — GAP-01 (closes v6.0 PARSE-07)

**Plans**: 5 plans

  - [x] 103-01-PLAN.md — i18n keys + Zustand store v2 + GAP-02 fixes + export query filter (GAP-01, GAP-02, WB-08, WB-09)

  - [x] 103-04-PLAN.md — CardView + SplitView + EvidenceDrawer components (WB-05, WB-06, WB-07, GAP-01)

**Closes v6.0 gaps**: UI-01 (ExtractionDialog `papers` prop wired from basket), PARSE-07 (`parsingSource` badge rendered), CRASH-02 (bare `useQuery` fixed in `EvidenceQuote` + `JobMetricsPanel`).

**UI hint**: yes

  2. User clicks "Connect Zotero" on the `/settings` page and is routed through the existing `convex/zotero/actions.ts:startOAuth` flow (OAuth 1.0a per Zotero's current 2025-09-24 API docs — they have NOT migrated to OAuth 2.0), returning to a connected state — ZOT-01

  6. A dev-guarded `purgeStaleZoteroState` internal action deletes all rows from `zoteroConnections` and `zoteroOAuthTokens` in the dev database, cleaning up pre-v7.0 orphan state encrypted with rotated keys — ZOT-06
**Plans**: 3 plans
