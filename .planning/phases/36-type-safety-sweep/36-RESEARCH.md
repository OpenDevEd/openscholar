# Phase 36: Type Safety Sweep - Research

**Researched:** 2026-03-02
**Domain:** Convex TypeScript type annotations (generated types, context parameters, API references)
**Confidence:** HIGH

## Summary

Phase 36 is a pure annotation change that replaces `any` casts with proper generated types across the Convex backend. The codebase already has all the necessary types generated in `convex/_generated/server.d.ts` (`MutationCtx`, `QueryCtx`, `ActionCtx`) and `convex/_generated/api.d.ts` (typed `internal`, typed `components`). Multiple files already use these types correctly (e.g., `convex/lib/auth.ts`, `convex/credits/internal.ts`, `convex/ai/helpers.ts`), so this phase follows established patterns.

The work is mechanical and low-risk. Every affected function already uses its context correctly at runtime -- the `any` casts just suppress type-checking. Removing them enables the TypeScript compiler to catch future regressions. The codebase currently compiles cleanly (only 3 pre-existing errors in test files, unrelated to this work).

**Primary recommendation:** Replace all `any` casts with generated types file-by-file, verify `npx tsc --noEmit` stays clean after each file, run tests at the end.

## Architecture Patterns

### Pattern 1: Context Type Annotations for Helper Functions

**What:** Convex auto-types the `ctx` parameter in mutation/query/action handler functions, but extracted helper functions need explicit annotations.

**When to use:** Any helper function outside the direct handler that receives `ctx` as a parameter.

**Example (already in codebase):**
```typescript
// Source: convex/lib/auth.ts (existing pattern)
import { QueryCtx, MutationCtx, ActionCtx } from "../_generated/server";

// Helper accepts the union when it only reads
async function getCurrentUser(ctx: AuthContext): Promise<Doc<"users"> | null> { ... }

// Helper that reads AND writes
async function getOrCreateUserFromIdentity(ctx: MutationCtx): Promise<Doc<"users">> { ... }

// Action helpers (for Node.js runtime functions)
async function requireActionAuth(ctx: ActionCtx) { ... }
```

**Key rules:**
- Functions that only read from `ctx.db` can use `QueryCtx` (or `QueryCtx | MutationCtx` if called from both)
- Functions that write (`ctx.db.insert`, `ctx.db.patch`, `ctx.db.delete`) must use `MutationCtx`
- Functions that call `ctx.runAction`, `ctx.runQuery`, `ctx.runMutation`, `ctx.storage`, or external APIs use `ActionCtx`
- `MutationCtx` extends `QueryCtx` (a mutation context can do everything a query context can)

### Pattern 2: Direct Use of Typed `internal` Export

**What:** The `internal` export from `convex/_generated/api` is already typed via `FilterApi<typeof fullApi, FunctionReference<any, "internal">>`. No `as any` cast needed.

**When to use:** Always. Replace `const internalApi = internal as any` with direct use of `internal`.

**Example:**
```typescript
// BEFORE (current code):
import { internal } from "../_generated/api";
const internalApi = internal as any;
await ctx.runMutation(internalApi.subscriptions.internal.markStripeEventFailed, { ... });

// AFTER (correct):
import { internal } from "../_generated/api";
await ctx.runMutation(internal.subscriptions.internal.markStripeEventFailed, { ... });
```

### Pattern 3: Direct Use of Typed `components` Export

**What:** The `components` export from `convex/_generated/api` is fully typed with all Stripe component methods (`components.stripe.public.*`, `components.stripe.private.*`).

**When to use:** Always. Replace `const componentApi = components as any` with direct use of `components`.

**Example:**
```typescript
// BEFORE (current code):
import { components } from "../_generated/api";
const componentApi = components as any;
await ctx.runQuery(componentApi.stripe.public.listInvoices, { ... });

// AFTER (correct):
import { components } from "../_generated/api";
await ctx.runQuery(components.stripe.public.listInvoices, { ... });
```

**Already used correctly in:** `convex/stripe.ts`, `convex/workpool.ts`, `convex/workflow.ts`.

### Pattern 4: Typed Patch Data

**What:** Use `Partial<Doc<"tableName">>` for patch objects instead of `any`.

**Example:**
```typescript
// BEFORE:
const patchData: any = { status: "completed", completedAt: Date.now() };

// AFTER:
import type { Doc } from "../_generated/dataModel";
const patchData: Partial<Doc<"extractionPapers">> = { status: "completed", completedAt: Date.now() };
```

**Note:** `Doc<"extractionPapers">` includes system fields (`_id`, `_creationTime`), so `Partial<Doc<"extractionPapers">>` allows all fields. The `ctx.db.patch()` call itself validates that only non-system fields are patched.

### Anti-Patterns to Avoid

- **Casting to `any` to avoid import errors:** Always import types from `../_generated/server` or `../_generated/dataModel`. If a type doesn't resolve, run `npx convex dev` to regenerate.
- **Using `QueryCtx` when `MutationCtx` is needed:** If the helper does `ctx.db.patch()` or `ctx.db.insert()`, it MUST be `MutationCtx`, not `QueryCtx`.
- **Removing `(q: any)` separately:** These will auto-resolve when `ctx` is properly typed, since the query builder gets its type from the context's `db` property.
- **Creating aliases for `internal`:** Using `const internalApi = internal` (even without `as any`) adds an unnecessary indirection. Use `internal` directly.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Context types | Custom interfaces for ctx | `MutationCtx`, `QueryCtx`, `ActionCtx` from `_generated/server` | Generated types stay in sync with schema automatically |
| Document types | Manual field interfaces | `Doc<"tableName">` from `_generated/dataModel` | Generated from schema, always accurate |
| API reference types | Manual function reference types | Typed `internal` and `components` from `_generated/api` | Generated API tree has full type information |

**Key insight:** Every type needed already exists in the `convex/_generated/` directory. No custom type definitions are required for this phase.

## Common Pitfalls

### Pitfall 1: QueryCtx vs MutationCtx Confusion

**What goes wrong:** Using `QueryCtx` for a helper that does writes, causing TypeScript to reject `ctx.db.patch()` calls.
**Why it happens:** Both `assertJobOwnership` in mutations.ts and `resolveOwnedJob` in queries.ts do read-only operations (`.get()`, `.query()`), but they live in different files -- mutations vs queries. The type must match the context they're called from.
**How to avoid:** Check the caller. If the function is called from a mutation handler, use `MutationCtx`. If from a query handler, use `QueryCtx`. If from both, use `QueryCtx` (since `MutationCtx` extends `QueryCtx`, a function typed `QueryCtx` accepts both).
**Warning signs:** TypeScript error "Property 'patch' does not exist on type 'DatabaseReader'".

### Pitfall 2: Renaming internalApi References

**What goes wrong:** Doing a find-and-replace of `internalApi` to `internal` but missing some occurrences, or accidentally replacing the import statement.
**Why it happens:** Multiple files use `internalApi` in dozens of locations (credits/actions.ts alone has ~20 references).
**How to avoid:** Delete the `const internalApi = internal as any;` line, then fix every compile error by replacing `internalApi` with `internal`. Use `replace_all` for the symbol rename within each file.
**Warning signs:** Runtime errors from undefined references.

### Pitfall 3: Forgetting the (q: any) Cascade Fix

**What goes wrong:** Replacing `ctx: any` with `QueryCtx` but leaving `(q: any)` in `.withIndex()` callbacks.
**Why it happens:** The `(q: any)` was only needed because `ctx` was `any`, making `ctx.db.query()` return `any`.
**How to avoid:** After fixing the ctx type, remove all `(q: any)` casts in the same file. The `q` parameter will be correctly inferred from the typed `ctx.db`.
**Warning signs:** TypeScript will NOT warn about unused `any` casts -- they just suppress useful type checking silently.

### Pitfall 4: Partial<Doc<>> vs Exact Patch Type

**What goes wrong:** `Partial<Doc<"extractionPapers">>` includes system fields (`_id`, `_creationTime`) that `ctx.db.patch()` doesn't accept.
**Why it happens:** `Doc<T>` includes system fields, `Partial<Doc<T>>` makes them all optional, but `patch()` only accepts non-system fields.
**How to avoid:** This is actually fine in practice because TypeScript checks structural compatibility at the `ctx.db.patch()` call site, not at the variable declaration. The `patchData` variable can be typed as `Partial<Doc<"extractionPapers">>` and the patch call will still type-check correctly since all values being set are valid non-system fields. Alternatively, if the compiler complains, use a more precise type from Convex: `Partial<Omit<Doc<"extractionPapers">, "_id" | "_creationTime">>`.
**Warning signs:** Type error at the `ctx.db.patch()` call saying system fields aren't assignable.

## Open Questions

1. **Should http.ts, credits/actions.ts, and test_helpers.ts ctx: any be in scope?**
   - What we know: These files have `ctx: any` but aren't explicitly listed in TYPE-01/02/03 (which only mention extraction mutations, queries, and workpoolActions).
   - What's unclear: Whether the phase scope should be strictly TYPE-01 through TYPE-06 or include all `ctx: any`.
   - Recommendation: Include them. Same mechanical fix, same risk profile, achieves the stated goal of "zero `ctx: any` parameters."

2. **Partial<Doc<"extractionPapers">> system field concern**
   - What we know: `Doc<T>` includes `_id` and `_creationTime`. `Partial<Doc<T>>` makes them optional.
   - What's unclear: Whether `ctx.db.patch()` will reject the type at compile time because it includes system fields.
   - Recommendation: Try `Partial<Doc<"extractionPapers">>` first. If TypeScript complains at the `patch()` call, use `Partial<Omit<Doc<"extractionPapers">, "_id" | "_creationTime">>` instead.
