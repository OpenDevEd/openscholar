<objective>
Fix out-of-order webhook state corruption and cancellation orphan records.

Purpose: Webhook handlers currently trust event payload data directly, which causes stale data to overwrite correct state when events arrive out of order. The cancellation handler creates orphan free-plan records and clears the stripeSubscriptionId, losing audit trail. These are two of the three confirmed critical billing bugs.

Output: Webhook handlers that always re-fetch from Stripe API (source of truth), cancellation that updates in-place, and selectCanonicalSubscription that handles the new data shape.
</objective>

2. **Create a shared `handleSubscriptionWebhook` helper function** (inside `http.ts`, before `registerRoutes`):
   ```typescript
   async function handleSubscriptionWebhook(
     ctx: any,
     event: Stripe.Event,
   ): Promise<void> {
     const eventSub = event.data.object as any;

     // Re-fetch from Stripe API (source of truth) -- per locked decision
     const fresh = await stripe.subscriptions.retrieve(eventSub.id);

     // Log divergence when event payload disagrees with re-fetched state
     // (groundwork for Phase 3 monitoring)
     const freshItem = fresh.items.data[0];
     const eventItem = eventSub.items?.data?.[0];
     if (
       fresh.status !== eventSub.status ||
       freshItem?.price?.id !== eventItem?.price?.id
     ) {
       console.warn("[WebhookDivergence]", {
         eventId: event.id,
         subscriptionId: eventSub.id,
         divergence: {
           status: { event: eventSub.status, fresh: fresh.status },
           priceId: {
             event: eventItem?.price?.id,
             fresh: freshItem?.price?.id,
           },
         },
       });
     }

     // Sync from fresh data, not event payload
     const stripeCustomerId =
       typeof fresh.customer === "string" ? fresh.customer : (fresh.customer as any)?.id;
     const currentPeriodEnd =
       fresh.current_period_end ?? freshItem?.current_period_end ?? Math.floor(Date.now() / 1000);
     const currentPeriodStart =
       fresh.current_period_start ?? freshItem?.current_period_start ?? Math.floor(Date.now() / 1000);

     await ctx.runMutation(internalApi.subscriptions.internal.syncSubscription, {
       stripeSubscriptionId: fresh.id,
       stripeCustomerId,
       status: normalizeStripeSubscriptionStatus(fresh.status),
       currentPeriodStart: currentPeriodStart * 1000,
       currentPeriodEnd: currentPeriodEnd * 1000,
       cancelAtPeriodEnd: isSubscriptionScheduledToCancel({
         cancelAtPeriodEnd: fresh.cancel_at_period_end ?? false,
         cancelAt: fresh.cancel_at ?? null,
         currentPeriodEnd,
       }),
       priceId: freshItem?.price?.id,
       quantity: freshItem?.quantity,
       metadata: fresh.metadata as Record<string, string>,
     });
   }
   ```

**Changes to `convex/subscriptions/lib/selectCanonicalSubscription.ts`:**

After the SUB-03 fix, canceled records will retain `stripeSubscriptionId`. Review and adjust the selection logic to ensure it still picks the correct record when both a canceled-with-Stripe-ID record and a new active record exist (for users who cancel and re-subscribe later).

The current priority order is:
1. Non-canceled paid with Stripe ID
2. Non-canceled paid
3. Non-canceled free
4. Any free
5. Any with Stripe ID
6. First

This order is correct because non-canceled records always win over canceled ones. However, step 5 ("any with Stripe ID") could now match a canceled record with a preserved Stripe ID. This is fine because it only triggers if there are no non-canceled records at all, which means the user truly has no active subscription.

**One adjustment needed:** In step 4 ("any free"), a canceled record with `plan: "free"` should not be preferred over a canceled record with a Stripe ID. But since step 4 already comes before step 5, and a canceled free-plan-in-place record IS a free record with a Stripe ID, it would match at step 4 AND step 5. This is acceptable -- step 4 finds it first.
