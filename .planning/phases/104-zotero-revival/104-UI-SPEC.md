## Interaction Specifications

### Zotero OAuth Connect Flow (ZOT-01)

1. User navigates to `/settings/connections`
2. If Zotero is disconnected, user sees card with "Connect Zotero" primary button
3. User clicks "Connect Zotero"
4. Button enters loading state (disabled, spinner icon replacing plug icon)
5. Client calls `api.zotero.actions.startOAuth({ callbackUrl: window.location.origin + "/api/zotero/callback" })`
6. On success, `window.location.href = authorizeUrl` redirects to Zotero's OAuth page
7. User authorizes on Zotero's site
8. Zotero redirects to `/api/zotero/callback` (Convex HTTP handler)
9. Handler calls `completeOAuth`, redirects to `/?zotero_connected=true` or `?zotero_error=...`
10. Settings page detects query param in `useEffect`, shows success/error toast via Sonner, cleans URL via `window.history.replaceState`

### Zotero Disconnect Flow (ZOT-01)

1. User sees connected state with "Disconnect" button (destructive outline variant)
2. User clicks "Disconnect"
3. Button transforms to inline confirmation: "Cancel" (text link) + "Confirm Disconnect" (destructive filled) -- same two-step pattern as wallet key revoke
4. User clicks "Confirm Disconnect"
5. Client calls `api.zotero.mutations.disconnect()`
6. On success: toast "Zotero disconnected.", card transitions to disconnected state
7. On error: toast "Failed to disconnect Zotero. Try again."
8. User clicks "Cancel": revert to single "Disconnect" button

### ZoteroTab Browse + Add Flow (ZOT-02, SEL-06)

1. User switches to Zotero tab on `/extraction/new`
2. Tab checks `useProtectedQuery(api.zotero.queries.getConnectionStatus)`
3. If `connected: false`: render empty state with link to `/settings/connections`
4. If `connected: true`: fetch collections via `api.zotero.actions.fetchCollections`
5. User selects a collection from the dropdown (or "All Items" default)
6. Tab fetches items via `api.zotero.actions.fetchItems({ collectionKey?, start: 0, limit: 25 })`
7. Items render with per-item state (see ZoteroItemRow States above)
8. User clicks checkbox on an item with a DOI -- triggers per-item resolution
9. Resolution calls `api.openalex.actions.resolveByDoi({ doi })` (Phase 100 action)
10. On success: item added to basket via `addToBasket({ rawId, title, doi, source: "zotero" })`
11. On failure: show red X with retry tooltip
12. User clicks "Load more" to fetch next page (`start: currentCount, limit: 25`)
13. Pagination appends (does not replace) -- cursor-based loading

### DOI Resolution Caching (D-10)

1. On first checkbox click for an item with DOI: call `resolveByDoi`, cache result in `Map<string, string | null>` local to `ZoteroTab`
2. If user unchecks and re-checks the same item: read from cache, skip API call
3. Cache is component-instance scoped -- cleared on unmount (navigating away from `/extraction/new`)
4. Failed resolutions are cached as `null` -- retry button clears that cache entry before re-calling

### OAuth Query Param Handling (D-03)

1. `ConnectionsPage` mounts a `useEffect` that reads `window.location.search`
2. If `?zotero_connected=true`: `toast.success(t("connectionsPage.zotero.oauthSuccess"))`, then `window.history.replaceState({}, "", window.location.pathname)`
3. If `?zotero_error=...`: `toast.error(t("connectionsPage.zotero.oauthError", { error }))`, then clean URL
4. Dependency array: empty `[]` (run once on mount)
5. Note: the callback redirects to `/?zotero_connected=true` (root), but the user may navigate to `/settings/connections` -- handle the param on both pages, or redirect the callback to `/settings/connections?zotero_connected=true` instead (implementation discretion per D-03)

## Accessibility Contract

| Requirement | Implementation |
|-------------|----------------|
