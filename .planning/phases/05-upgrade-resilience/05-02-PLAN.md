});

**What to insert:**

```typescript
  // --- Upgrade proration detection (UPGR-01) ---
  // When classifyMonthlyCreditInvoice returns "ignore_non_recurring" for a
  // subscription_update invoice, check if this is an upgrade proration invoice
  // by reading upgrade metadata from the Stripe subscription.
  if (
    decision.decision === "ignore_non_recurring" &&
    invoiceBillingReason === "subscription_update" &&
    stripeSubscriptionId
  ) {
    const subscription = await stripe.subscriptions.retrieve(stripeSubscriptionId);
    const meta = subscription.metadata ?? {};
    const upgradeFromPlan = meta.upgradeFromPlan;
    const upgradeToPlan = meta.upgradeToPlan;
    const upgradeTimestamp = meta.upgradeTimestamp;

    if (upgradeFromPlan && upgradeToPlan && upgradeTimestamp) {
      // Resolve the user from the subscription via internal query
      const subRecord = await ctx.runQuery(
        internalApi.subscriptions.internal.getSubscriptionByStripeId,
        { stripeSubscriptionId },
      );

      if (subRecord?.userId) {
        // Read period boundaries from the fresh Stripe subscription object
        // (not local DB -- may be stale when webhook fires before syncSubscription)
        const sub = subscription as any;
        const periodStartMs = (sub.current_period_start ?? 0) * 1000;
        const periodEndMs = (sub.current_period_end ?? 0) * 1000;

        const grantResult = await ctx.runMutation(
          internalApi.credits.internal.grantUpgradeProRataCredits,
          {
            userId: subRecord.userId,
            fromPlan: upgradeFromPlan,
            toPlan: upgradeToPlan,
            currentPeriodStartMs: periodStartMs,
            currentPeriodEndMs: periodEndMs,
            stripeSubscriptionId,
          },
        );

        console.log("[processInvoiceForGrant] Upgrade proration credit grant via webhook path", {
          stripeInvoiceId: args.stripeInvoiceId,
          stripeSubscriptionId,
          upgradeFromPlan,
          upgradeToPlan,
          outcome: grantResult.outcome,
          grantedCredits: grantResult.grantedCredits,
        });

        return {
          outcome: grantResult.outcome,
          message: grantResult.message,
          usedFallbackSubscription,
        };
      }
    }

    // No upgrade metadata or no user found -- fall through to normal ignore
    // (This preserves existing behavior for non-upgrade subscription_update invoices)
  }
```

**Where exactly:** This block must go AFTER the retry_with_reconcile check block AND before the `const result = await ctx.runMutation(internalApi.credits.internal.grantMonthlyCredits, ...)` call. The flow is:

1. `classifyMonthlyCreditInvoice` runs (existing)
2. `retry_with_reconcile` check runs (existing)
3. **NEW: upgrade proration check** (if `ignore_non_recurring` + `subscription_update` + has metadata -> call grantUpgradeProRataCredits and return)
4. Falls through to `grantMonthlyCredits` (existing -- for `grant` decisions)

CRITICAL ANTI-PATTERNS TO AVOID:
- Do NOT add `subscription_update` to `ELIGIBLE_MONTHLY_CREDIT_BILLING_REASONS` -- this would cause double-grants
- Do NOT read period boundaries from local DB -- use the Stripe subscription object
- Do NOT add a new dedup mechanism -- the existing `grantUpgradeProRataCredits` dedup is sufficient
- Do NOT clear upgrade metadata after processing -- dedup protects against re-granting

Note: The `grantUpgradeProRataCredits` mutation uses `planValidator` which expects specific plan string values. The `upgradeFromPlan` and `upgradeToPlan` from metadata are plain strings. This is safe because the metadata was written by `changePlan` which uses the same plan values. However, if Convex runtime validation rejects the metadata strings, cast them appropriately.
