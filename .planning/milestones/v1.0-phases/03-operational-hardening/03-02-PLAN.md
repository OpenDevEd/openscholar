Add a JSDoc TOCTOU CONTRACT block on the `deductCredits` mutation in `convex/credits/internal.ts` (line 1077). Follow the same style as the DEDUP CONTRACT on `grantMonthlyCredits`.

The documentation must cover these aspects per locked decision:
1. **Current protection**: Convex OCC provides serializable transactions within a single mutation. The `deductCredits` mutation reads the balance, checks sufficiency, and writes the deduction atomically. Two concurrent calls to `deductCredits` will serialize via OCC -- one succeeds, the other retries with fresh data and either succeeds (if balance sufficient) or throws `INSUFFICIENT_CREDITS`.

2. **Theoretical risk window**: The real TOCTOU risk is NOT within the mutation itself, but at the ACTION level. The pattern `query(checkBalance) -> ... -> mutation(deductCredits)` has a gap between the balance check and the deduction. During this gap, another concurrent action could also pass the check, leading to both attempting deduction. However, because `deductCredits` RE-READS the balance inside the mutation and throws if insufficient, the OCC protection catches this: one mutation deducts successfully, the other retries with the updated (lower) balance and either succeeds or throws.

3. **Why this is safe TODAY**: The mutation-level re-read + OCC retry is sufficient protection. A user cannot end up with a negative balance because the sufficiency check is INSIDE the mutation, not just in the calling action. The worst case is a spurious `INSUFFICIENT_CREDITS` error for a legitimate concurrent request, which is the correct behavior.

4. **Trigger for additional mitigation**: Per locked decision, the trigger is an observed incident (real double-deduction in production), NOT a user count threshold. If a double-deduction is ever observed, it would indicate a bug in the mutation logic itself (the re-read was bypassed somehow), not an OCC failure.

5. **Recommended mitigation path (for when trigger hits)**: Two options to document:
   - Option A: Ensure ALL callers of `deductCredits` go through a single action gateway that serializes requests per user (e.g., Convex workpool with `maxParallelism: 1` per userId).
   - Option B: Add a version/sequence field to the credits record and check it in the mutation (optimistic locking on top of OCC -- belt and suspenders).
   - Recommendation: Option A is simpler and leverages existing Convex primitives.
